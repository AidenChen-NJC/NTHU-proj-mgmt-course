# MVP 1 — 應收帳款動態定價系統 (Reverse Factoring Dynamic Pricing)

**Codename：** `reverse-factoring`
**排序：** **第二棒**
**開發窗：** M6 – M10
**Pilot：** M10 – M14（與 MVP 3 整合上線）

---

## 1. North Star
**用核心買方信用解放 SME 應收帳款現金流。** 將傳統靜態、保守的應收帳款融資定價，轉為動態、即時的演算法定價，讓 SME 在發票確認當下即可取得現金。

## 2. 用戶
- **First User：** 銀行 RM（客戶經理）+ 核貸專員
- **End Beneficiary：** 對核心大廠出貨的 Tier-1 / Tier-2 SME 供應商

## 3. 痛點
- 傳統保理利率僵化，常常因風險評估保守而報價過高，SME 不接受
- 人工撥款流程長（通常 5-10 天），與「現金流救急」需求脫節
- 銀行 RM 缺乏即時定價工具，每筆案子都要回辦公室算

## 4. 計量邏輯
```
動態利率 = 資金成本 (funding cost)
         + 核心買方信用風險貼水 (buyer credit risk premium based on PD)
         + 期限貼水 (tenor premium)
         + 操作成本 (ops cost)
         + 流動性溢酬 (liquidity premium)
```
- **核心買方 PD：** 取自既有銀行內部信評系統（**這是橋接舊系統的關鍵點**）
- **動態調整：** 隨市場 funding cost 與買方 PD 變化每日 refresh

## 5. 數據源
| 數據 | 來源 | 整合複雜度 |
|---|---|---|
| 核心買方信評 / PD | 銀行既有信評系統 | **中** — 需風控部 API 介接 |
| 應收帳款 / 發票 | 核心買方 ERP / SCM | **高** — 需與第一個試點大廠系統整合 |
| 市場 funding rate | 既有財務系統 | 低 |
| 歷史保理成交利率 | 銀行內部 | 低 |

## 6. 介面（Streamlit）
- 發票批次匯入
- 即時定價試算（單筆 + 批次）
- 撥款試算 + 條件對照
- 歷史成交回測對比

## 7. 成功指標
- **Done：** 對歷史成交發票回測，定價誤差 < 預設閾值
- **Leading：** 每週新增可定價發票數 / 整合的買方系統數
- **Lagging：** 試點期撥款金額、平均撥款時間從 X 天縮短至 Y 小時

## 8. 排序理由（為何不是第一棒）
- **觸碰核心信評系統：** 需風控部開放 PD API——這在 MVP 3 已建立 14 個月 credibility 後較容易談
- **需要核心大廠配合：** 系統整合成本高，需先有試點意向
- **政治風險中等：** 不直接挑戰風控決策權，但會被質疑「動態定價是否太激進」
- 但仍**不是最敏感的**——因為定價是 RM 的事，風控仍可在 Definition of Done 設置上限與否決權

## 9. 風險
- 核心買方系統整合工程量超估
- KYC/AML 仍由原核心系統處理——銜接點需明確設計
- 動態定價若被市場炒作為「銀行降標」，需法遵預先溝通

- [ ] 既有信評系統 PD 是否能以 API 取得？是否需先做 IT 改造？
- [ ] 法遵 / 監理對「動態定價」是否有明文規範？
